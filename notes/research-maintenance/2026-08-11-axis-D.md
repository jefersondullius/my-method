## Task 5 — Fable 5's cybersecurity-domain fallback

- Source: <https://code.claude.com/docs/en/model-config.md> — accessed 2026-08-11,
  sections `### Work with Fable 5`, `### Automatic model fallback`,
  `#### Security research and biology workloads`.
- **Verdict: STILL DOCUMENTED — and now more specific than the baseline recorded.**

VERBATIM:

> Fable 5 is not the default model. Select it with `/model fable`. Requests that its safety classifiers flag, most often in cybersecurity and biology domains, trigger [automatic model fallback](#automatic-model-fallback).

> Fable 5 and Opus 5 run with safety classifiers for cybersecurity and biology content. When a classifier flags a request and the flagged category has a fallback model, Claude Code re-runs the request on that model and shows a notice in the transcript. The fallback model depends on which model refused and which category was flagged:
>
> * **Fable 5**: biology-flagged requests re-run on Opus 5, and cybersecurity-flagged requests re-run on Opus 4.8.
> * **Opus 5**: cybersecurity-flagged requests re-run on Opus 4.8. Biology-flagged requests end with a refusal instead, because Opus 5 runs its own biology classifiers with no fallback model.

> Category-based fallback requires Claude Code v2.1.219 or later. Before v2.1.219, every flagged Fable 5 request re-ran on your provider's default Opus model, and Opus 5 was not a fallback source.

> Workloads in offensive security or biology, including penetration testing, Capture the Flag (CTF) exercises, and biology-adjacent codebases, trigger fallback frequently, often on the first request. … This is expected routing for these domains, not an account flag.

> Fallback can trigger on the first request of a session, before you send anything unusual, because the first request carries workspace context such as your CLAUDE.md content and git status. A repository that contains security or biology material can trip the classifier on that context alone.

Also VERBATIM, an opt-out the baseline did not record:

> To decide what happens each time a request is flagged, rather than switching automatically, run `/config` and turn off **Switch models when a message is flagged**, or set [`switchModelsOnFlag`](/docs/en/settings#available-settings) to `false` in your settings file.

**What this means for method v7's UP trigger, concretely.** The UP trigger fires when a
card carries REVIEW security rows on `authentication`, `authorization` or `payments`
(`kit/my-method/commands/start-project.md:663-668`). Three consequences, all sourced above:

1. **Recommending `fable` on such a card is self-defeating on cybersecurity content**: the
   request is re-run on **Opus 4.8**, a *weaker* model than the Opus 5 that `opus` resolves
   to on the Anthropic API. Recommending `fable` for a security card can therefore land the
   user on a lower tier than recommending `opus` would have.
2. **`opus` is not immune either** — Opus 5 cybersecurity flags also re-run on Opus 4.8.
   But `opus` is the safer recommendation of the two, because it degrades one step instead
   of two and never refuses outright on this category.
3. **The classifier can fire on repository context alone** (CLAUDE.md, git status), so a
   security-flavoured project can be routed away from the recommended model on the *first*
   request, before the card's prompt is even read. Nothing in the kit detects this. The
   only documented way to see it is the transcript notice, or `claude --safe-mode` to test
   whether customizations are the trigger.

This upgrades the baseline's generic warning into an actionable one: **method v7's UP
trigger should prefer `opus` over `fable` on security cards**, or say nothing. That is a
recommendation for the parent to weigh, not a change made here.
