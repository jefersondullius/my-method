## BUILT-IN EQUIVALENT CHECKS

Five things this kit hand-rolls, each checked for a documented built-in
equivalent. **Every finding below pre-dates 2026-08-10**, so none is an
axis-E candidate — but each is reported because knowing a built-in

### 1. Session/state handoff and memory → **EXISTS AND PARTIALLY DUPLICATES**

**What exists:** *Auto memory*, documented at
`https://code.claude.com/docs/en/memory` (accessed 2026-08-11).
Claude writes its own notes to `~/.claude/projects/<project>/memory/`,
keyed to the git repository and shared across worktrees. `MEMORY.md` is
an index loaded into **every** conversation (first 200 lines or 25 KB).
On by default; toggled with `autoMemoryEnabled` or `/memory`.

**When it shipped:** v2.1.59, **2026-02-26** ("Claude automatically
saves useful context to auto-memory. Manage with /memory"), with
`autoMemoryDirectory` added in v2.1.74 (2026-03-12) and worktree
sharing in v2.1.63 (2026-02-28). Roughly five months before this
repository's first commit.

**Named targets it touches:** `method.md` → "FILES THAT CARRY STATE"
(the whole section, including its rule "if information exists only in
this conversation, it does not exist"); `method.md` STEP 5d; and
`kit/my-method/templates/STATE.md`.

**What it does NOT replace, and why STATE.md stands:**
- Auto memory is **machine-local** and not in git; STATE.md is
  committed and is one of the three status files STEP 5d requires in
  the same commit, and that `kit/my-method/hooks/verify-gate.ps1`
  denies a commit for missing.
- Auto memory is **Claude-curated** — the docs say Claude "decides
  what's worth remembering"; STATE.md is a specified structure with
  seven named sections that `where-am-i.md` and `next-task.md` read
  by name.
- Only the **first 200 lines / 25 KB** of `MEMORY.md` load. STATE.md's
  80-line cap is a design choice, not a truncation an agent must
  defend against.

**Cost of adopting it anyway:** none to install (on by default), but
it would introduce a second place a project fact can live, with no
rule saying which one owns it. That is a real hazard, and the method
currently does not mention auto memory at all.

**Verdict: not a candidate.** It pre-dates the method and does not make
STATE.md obsolete. The genuinely useful observation is narrower: **the
method never declares that auto memory exists or which store owns a
fact.** That is a documentation gap for a future run to weigh, not an
obsolescence.

### 3. Security review / scanning → **EXISTS AND PARTIALLY DUPLICATES (three layers)**

Anthropic documents a five-layer security stack at
`https://code.claude.com/docs/en/claude-security#how-the-plugin-fits-with-other-security-tools`
(accessed 2026-08-11). Three layers touch this repo:

**(a) `/security-review` — built-in command.** Verbatim from
`https://code.claude.com/docs/en/commands.md` (accessed 2026-08-11):
"Analyze the changes on your current branch for security
vulnerabilities. Reviews the diff between your branch and origin's
default branch, identifying risks like injection, auth issues, and data
exposure. **Needs an `origin` remote**".
*Named target:* `kit/my-method/agents/security-reviewer.md` and the
REVIEW branch of `method.md` STEP 5c.
*Why it does not replace it:* it reviews **branch vs `origin`'s default
branch**, not the task's diff, and it **requires an `origin` remote** —
a T0 local-only project started by `start-project.md` has none. It is
also not keyed to `SECURITY-MATRIX.md` row IDs, so its output cannot be
recorded per-row on a card the way STEP 5c requires. Already known to
this repo: `notes/maintenance/WATCHLIST.md` axis C says "Try
Semgrep-in-verify + built-in `/security-review` first".

**(b) `claude-security` plugin — the one this repo's audits never
evaluated.** `https://code.claude.com/docs/en/claude-security`
(accessed 2026-08-11), announced Week 30, **July 20–24, 2026**.
`/plugin install claude-security@claude-plugins-official`, one command
`/claude-security`, three jobs (scan codebase / scan changes / suggest
patches). Multi-agent: agents map architecture, build a threat model,
hunt vulnerabilities, and **independently verify every finding**.
Writes to `CLAUDE-SECURITY-<timestamp>/` with `RESULTS.md`,
`RESULTS.jsonl`, and a revision stamp tying the report to the exact
commit scanned. Patches are **never applied automatically**.
*Named target:* same as (a) — `kit/my-method/agents/security-reviewer.md`
and STEP 5c's REVIEW branch; secondarily the REVIEW rows of
`playbook/SECURITY-MATRIX.md` (1.2, 1.3, 2.2, 3.1, 3.4, 4.1, 4.3, 5.1,
5.2, 6.1, 7.2, 9.2).
*Cost, stated by its own docs:* Claude Code v2.1.154+, a **paid plan**
(on Pro, dynamic workflows must be turned on in `/config`); `python3`
≥ 3.9.6 on PATH; "may take a while, may use a significant number of
tokens"; each scan counts against plan usage limits; "works best in
auto mode"; and **"Scans are nondeterministic: two scans of the same
code can surface different findings."**
*Verdict: NOT an axis-E candidate* — it shipped ~3 weeks **before**
this repository's first commit, so it fails the "did not exist when
this method was written" test. It also does not replace the reviewer:
it is unkeyed to matrix row IDs, its unit of output is a report
directory rather than a per-card finding, it is nondeterministic (STEP
5c's fix loop requires a fresh reviewer to clear the *same* row), and
its patch flow directly contradicts the reviewer's structural
read-only guarantee (`tools: Read, Grep, Glob`). It is a plausible
*addition* at a real T2/T3 project, on the same DEFERRED footing as
`security-guidance` in `WATCHLIST.md` axis C — not a replacement.

**Bonus, independently useful:** this page confirms
`LAST-CHECK.md` finding 3 and `WATCHLIST.md` axis D's Fable-5 row from
a **second** source. Verbatim: *"You may see 'Fable 5's safeguards
flagged this message' when using Fable 5. Due to Fable 5's
cybersecurity safety classifiers, certain model activities will be
blocked and automatically downgraded to Opus."* The fallback is real,
still documented on 2026-08-11, and lands exactly where method v7's UP
trigger fires.

**(c) `security-guidance` plugin.** Already carried as DEFERRED in
`WATCHLIST.md` axis C. No change found; not re-derived here.

### 4. Pre-commit / verification gate → **NO BUILT-IN FOUND**

`https://code.claude.com/docs/en/hooks` (accessed 2026-08-11) lists
**31** lifecycle events: SessionStart, Setup, UserPromptSubmit,
UserPromptExpansion, PreToolUse, PermissionRequest, PermissionDenied,
PostToolUse, PostToolUseFailure, PostToolBatch, Notification,
MessageDisplay, SubagentStart, SubagentStop, TaskCreated,
TaskCompleted, Stop, StopFailure, TeammateIdle, InstructionsLoaded,
ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate,
WorktreeRemove, PreCompact, PostCompact, Elicitation,
ElicitationResult, SessionEnd.

**There is no commit, pre-commit, or verification-gate event, and no
native git-hook integration.** `PreToolUse` is still documented as the
event that "Can block it", and `permissionDecision: "deny"` with
`permissionDecisionReason` is still the documented blocking shape —
exactly what `kit/my-method/hooks/hooks.json` and
`kit/my-method/hooks/verify-gate.ps1` use.

The built-in `/verify` is **not** an equivalent. Verbatim from
`commands.md`: "Confirm a code change does what it should by building
your project's app, running it, and observing the result, rather than
relying on tests or type checks. Requires Claude Code v2.1.145 or
later." It builds and drives the app; it does not re-run an accumulated
regression set, does not write machine evidence, and blocks no commit.
`method.md` STEP 5c's `scripts/verify.ps1` entrypoint and its
`.claude/last-verify.json` evidence file have no built-in counterpart.

*(Note for the next run: `scripts/verify.ps1` does not exist in this
repository — it is prescribed by `method.md` STEP 5c and
`kit/my-method/templates/CLAUDE.md` for the projects the method
creates. The only verify script here is
`kit/my-method/hooks/verify-gate.ps1`.)*

### 5. Plugin health / doctor command → **EXISTS AND PARTIALLY DUPLICATES**

**What exists:** `/doctor` (alias `/checkup`), a **bundled skill**,
documented at `https://code.claude.com/docs/en/commands` (accessed
2026-08-11). Became "a full setup checkup that can diagnose and fix
issues" in **v2.1.205, 2026-07-08** — a month before this repository's
first commit. It checks installation health, duplicate/leftover
installs, `PATH`, unparseable settings, **"unused skills, MCP servers,
and plugins versus their context cost"**, slow hooks, and whether a
newer version exists on the release channel. `claude doctor` from the
terminal prints read-only diagnostics without starting a session.
Related changelog entries confirm it also surfaces stale
`enabledPlugins` entries (v2.1.?, line 1455), plugin component-folder
warnings (line 1755), MCP schema errors (line 1851), and hook
misconfiguration (line 1608).

**Named target:** `kit/my-method/commands/health-check.md`, probe 1
("is the right plugin loaded, and is it the current one?").

**What `/doctor` covers of probe 1:** whether the plugin loaded, is
enabled, has load errors, and whether a newer version exists.

**What `/doctor` does NOT cover — the other four probes stand
untouched:**
- probe 1's second half: comparing `claude plugin details my-method`'s
  component inventory against the **kit on disk** (`commands/*.md`,
  `agents/*.md`, `hooks/hooks.json` entries). `/doctor` has no notion
  of "the kit that was last applied".
- probe 2: does the `security-reviewer` subagent actually register and
  answer.
- probe 3: does the commit gate actually **DENY** a
  `git commit --dry-run --allow-empty`. This is the kit's only Level-1
  mechanism and nothing built-in tests that a specific hook fires.
- probe 4: are `git`, `semgrep`, `gitleaks`, `npm`, `pip-audit`
  present.
- probe 5: `claude plugin validate ./kit/my-method`.

**Verdict: not a candidate.** It pre-dates the method, and it makes
roughly half of one probe out of five redundant. `health-check.md`
stands. Worth one line in a future proposal: probe 1 could say "run
`claude doctor` first for install-level problems" instead of
re-deriving them.
